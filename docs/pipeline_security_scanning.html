DevSecOps + Infraestructura como Código

El pipeline CI/CD de Azure DevOps pasó de un flujo lineal (build → push → deploy) a uno con cinco stages, puertas de calidad (gates) de seguridad que bloquean el deploy ante vulnerabilidades o secretos, y provisión de infraestructura con Terraform integrada al propio pipeline.

📦 Proyecto: dimo3-frontend 📅 Fecha: Julio 2026 🌿 Rama: main 📄 Pipeline: azure-pipelines.yml

💡 Filosofía Shift Left Security: las verificaciones de seguridad se ejecutan lo más temprano posible en el ciclo de vida del desarrollo (pre-build), de modo que los problemas se detectan antes de que el código llegue a producción, reduciendo costo y riesgo.

🔍 CodeScan — Puerta de calidad pre-build

  • NodeTool@0 — instala Node 20.x para el toolchain npm
  • npm ci — instala dependencias desde el lockfile
  • ESLint — linter: errores bloquean, warnings permitidos
  • npm audit — vulnerabilidades: CRITICAL bloquea, HIGH reporta
  • Gitleaks — secret scan sobre todo el historial git (fetchDepth: 0)

⚠️ Defensa en profundidad: cada stage es un filtro. Si CodeScan falla, no se construye nada (ahorra recursos). Si ImageScan falla, la imagen está en ECR pero el deploy se bloquea, permitiendo investigar antes de impactar producción.

🛠️ Herramientas Utilizadas

Cada herramienta cubre una capa distinta de la superficie de ataque.

Herramienta Tipo Qué detecta Dónde corre
ESLint Linter Errores de código, bugs potenciales, malas prácticas en TS/React CodeScan (pre-build)
npm audit SCA (Software Composition Analysis) Vulnerabilidades conocidas en el árbol de dependencias npm CodeScan (pre-build)
Gitleaks Secrets Scanner API keys, tokens, contraseñas commiteadas (en todo el historial git) CodeScan (pre-build)
Trivy Container Image Scanner CVEs del SO (Alpine) + paquetes npm en la imagen final ImageScan (post-build)
Trivy CycloneDX SBOM Generator Inventario de componentes con versiones exactas ImageScan (artifact)

Comando exacto del gate de Trivy

bash trivy image --severity HIGH,CRITICAL \ --exit-code 1 # retorna error si hay hallazgos \ --ignore-unfixed # ignora CVEs sin patch disponible \ <imagen>

📦 ¿Para qué sirve el SBOM? Si se descubre un CVE nuevo, podés buscar en el SBOM si esa versión vulnerable está en producción. También sirve para auditorías de cumplimiento y gestión de licencias.

Mecanismo de overrides en package.json

Para forzar versiones parcheadas de dependencias transitivas (que npm audit fix no puede resolver sin romper), se usó el campo overrides:

package.json "overrides": { "tar": "^7.5.19", "sharp": "^0.35.0", "sigstore": "^4.1.1", "picomatch": "^4.0.4", "brace-expansion": "^2.1.2" }

🌍 Infraestructura como Código (Terraform)

La infraestructura AWS que antes se asumía pre-existente y creada a mano ahora se provisiona y gestiona con Terraform, integrado al pipeline como un stage más.

💡 Antes vs. ahora: el ECR, el cluster ECS, los roles IAM, el log group y la task definition debían existir en AWS antes de correr el pipeline (creados manualmente, sin versionado). Con Terraform, toda esa infraestructura vive versionada en terraform/ y se aplica automáticamente en cada push a main.

Recursos gestionados por Terraform

Recurso AWS Tipo Terraform Detalle
Repositorio ECR dimo-frontend aws_ecr_repository Scan on push + lifecycle policy (10 imágenes + expirar sin tag)
Cluster ECS dimo-prod-cluster aws_ecs_cluster Container Insights habilitado
Rol IAM de ejecución aws_iam_role Pull de ECR + escritura de logs (AmazonECSTaskExecutionRolePolicy)
Rol IAM de tarea aws_iam_role Vacío (el frontend no llama a AWS directamente)
Task definition Fargate aws_ecs_task_definition awsvpc, 256 CPU / 512 MB, puerto 3001, healthCheck wget
Service ECS dimo-frontend-svc aws_ecs_service Fargate + security group, ignore_changes en imagen/conteo

⚠️ Log group fuera de Terraform: el log group de CloudWatch (/ecs/dimo-frontend) se gestiona fuera de Terraform porque la service connection no tiene permisos de logs:TagResource / logs:ListTagsForResource. El task definition lo referencia por nombre. El resto sí lo gestiona Terraform.

Cómo se integra al pipeline

El stage Terraform corre entre ImageScan y Deploy. Ejecuta la secuencia completa de Terraform con las credenciales de la service connection AWS:

stage Terraform terraform fmt -check # gate: falla si los .tf no están formateados terraform init -input=false terraform validate terraform plan -input=false -out=tfplan terraform apply -input=false -auto-approve tfplan

Import de recursos pre-existentes

Algunos recursos (ECR, cluster, service) ya existían en AWS, creados manualmente antes de Terraform. Para que Terraform los adoptara en vez de intentar recrearlos, se usaron bloques import declarativos:

main.tf import { to = aws_ecr_repository.frontend id = "dimo-frontend" } # ... idem para aws_ecs_cluster.main y aws_ecs_service.frontend

State: persistencia y advertencias

El state es local (sin backend remoto). Para que sobreviva entre runs, el terraform.tfstate se publica como artifact (terraform-state) y se descarga al inicio del run siguiente usando DownloadPipelineArtifact@2 con latestFromBranch.

⚠️ Riesgo del state local en CI: si dos runs se superponen o el artifact se pierde, puede haber drift. Para un entorno de producción real se recomienda migrar a un backend remoto (S3 + DynamoDB para locking). Queda fuera del alcance actual.

Acceso al frontend: IP efímera

Al final del deploy, el pipeline lista las tareas RUNNING y resuelve la IP pública de cada una (vía su ENI), imprimiendo http://<IP>:3001 en el log del step “Mostrar IP pública del frontend”.

⚠️ La IP cambia en cada deploy, porque no hay Load Balancer: la tarea Fargate recibe una IP pública nueva en cada rolling. Para una URL estable haría falta un ALB (Application Load Balancer), aún no provisionado.

Estructura de archivos

terraform/ providers.tf # provider AWS + required_version (state local) variables.tf # región, nombres, cpu/memory, account_id, vpc main.tf # recursos: ECR, cluster, IAM, task def, service + imports outputs.tf # URIs y ARNs útiles terraform.tfvars.example # plantilla (copiar a terraform.tfvars)

⚙️ Archivos de Configuración

Archivos creados para gestionar falsos positivos y excepciones justificadas.

.trivyignore

Lista de CVEs que Trivy debe ignorar durante el image scan. Cada entrada debe estar justificada.

Contenido actual: 5 CVEs de librerías del npm embebido en node:22-alpine (tar, sigstore, picomatch, brace-expansion). Estas librerías se usan únicamente en build time para instalar dependencias. La imagen de producción (stage runner) ejecuta node server.js y no expone npm, por lo que no son explotables en runtime.

🔧 Fix real futuro: migrar a imagen distroless/slim sin npm en producción.

.gitleaksignore

Permite listar falsos positivos de Gitleaks mediante su fingerprint (formato JSONL). Actualmente vacío: Gitleaks no detectó secretos en el escaneo inicial sobre 51 commits.
